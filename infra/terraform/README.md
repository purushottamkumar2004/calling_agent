AWS infrastructure in ap-south-1 (ADR 0004, 0007). Direction and sizing: [staging-plan.md](staging-plan.md).

**Status: written and validated, not applied.** Staging is applied at the end of Phase 2, before the first clinic (ADR 0010).

```

modules/
  network/            VPC: public / private-app / private-data tiers, NAT, S3 endpoint, workload SG
```

## Checks (CI and local, no AWS credentials needed)

```bash
cd infra/terraform
terraform fmt -check -recursive
terraform -chdir=envs/staging init -backend=false && terraform -chdir=envs/staging validate
terraform -chdir=envs/staging test     # full plan against mocked providers, with assertions
```

## Applying staging (end of Phase 2)

Prerequisites: an AWS Organizations member account for staging, admin access via SSO, Terraform >= 1.11.

1. **State bucket** (once per account):
   ```bash
   cd infra/terraform/bootstrap
   terraform init && terraform apply -var aws_account_id=<staging-account-id>
   ```
   Its state is local. Keep `terraform.tfstate` safe (password manager or a private location) or migrate it into the bucket afterwards with a `backend "s3"` block.
2. **Staging**:
   ```bash
   cd ../envs/staging
   cp backend.hcl.example backend.hcl            # set bucket = <state_bucket output>
   cp terraform.tfvars.example terraform.tfvars  # set aws_account_id
   terraform init -backend-config=backend.hcl
   terraform providers lock -platform=linux_amd64 -platform=darwin_arm64 -platform=darwin_amd64
   terraform plan -out=staging.tfplan            # review, then: terraform apply staging.tfplan
   ```
   Commit the generated `.terraform.lock.hcl`.
3. **GitHub**: create Environments `staging` (deployment branch: `main`) and `staging-migrations` (`main` + required reviewer). Set variable `AWS_DEPLOY_ROLE_ARN` = output `github_deploy_role_arn` on both.
4. **App login role**: a one-off ECS task creates the `calling_agent_app` role (member of `api_app`) from the `postgres_app_secret_arn` secret, after the first migration. Built with the compute layer.

## Design notes

- **Secrets**: the RDS owner password is generated and rotated by RDS in Secrets Manager (never in state). The app DB login and Redis AUTH token are generated by Terraform (`random_password`), stored in Secrets Manager, and therefore also in state, which is KMS-encrypted in S3 with versioning.
- **Postgres** forces TLS (`rds.force_ssl=1`): connection strings need `sslmode=require`. The owner (RDS master user, `calling_agent`) is not a superuser and has `CREATEROLE`, matching local dev and CI.
- **Redis** is node-based with `maxmemory-policy noeviction` (BullMQ) and TLS + AUTH: URLs are `rediss://`.
- **Data tier** subnets have no route to the internet. Postgres and Redis admit only the workload security group.
- **Deploy role** trusts only jobs bound to the `staging` / `staging-migrations` Environments of this repository; it can push to `calling-agent/*` ECR repos, update services and run one-off tasks in the staging cluster, and pass only `calling-agent-staging-ecs-*` roles to ECS.
