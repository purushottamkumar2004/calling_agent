# infra/terraform

AWS infrastructure in ap-south-1 (ADR 0004, 0007), managed with **OpenTofu 1.12.9** everywhere: locally, in CI and for applies (ADR 0012). Direction and sizing: [staging-plan.md](staging-plan.md).

Install the pinned version (same as CI): download `tofu_1.12.9` for your OS from the [OpenTofu releases](https://github.com/opentofu/opentofu/releases/tag/v1.12.9), or use a version manager such as `tenv`. The folder keeps the name `terraform/` and the files stay `.tf`; OpenTofu reads them as-is.

**Status: written and validated, not applied.** Staging is applied at the end of Phase 2, before the first clinic (ADR 0010).

```
bootstrap/            one-time per account: S3 state bucket (local state)
modules/
  network/            VPC: public / private-app / private-data tiers, NAT, S3 endpoint, workload SG
  data/               KMS, RDS Postgres 16, ElastiCache Redis 7, recordings bucket, DB/Redis secrets
  github-oidc/        GitHub Actions deploy role (OIDC, no AWS keys in GitHub)
  ecr/                one repository per app (immutable tags, scan on push, expiry)
  ecs-cluster/        cluster + Cloud Map namespace `internal` (api.internal, otel.internal)
  edge/               delegated Route 53 zone, ACM wildcard cert, public ALB (HTTPS, host routing)
  ecs-service/        one Fargate service or one-off task: roles, task def, ALB rule, Cloud Map, schedule
envs/
  staging/            composition: main.tf (network, data, OIDC), compute.tf,
                      secrets.tf, observability.tf; tests/ = offline plan tests with mocked providers
```

## Checks (CI and local, no AWS credentials needed)

```bash
cd infra/terraform
tofu fmt -check -recursive
tofu -chdir=envs/staging init -backend=false && tofu -chdir=envs/staging validate
tofu -chdir=envs/staging test     # full plan against mocked providers, with assertions
```

Once a root has a committed `.terraform.lock.hcl`, CI runs `init -lockfile=readonly` there and fails if the lock file is out of date (ADR 0012).

## Applying staging (end of Phase 2)

Prerequisites: an AWS Organizations member account for staging, admin access via SSO, OpenTofu 1.12.9.

1. **State bucket** (once per account):
   ```bash
   cd infra/terraform/bootstrap
   tofu init && tofu apply -var aws_account_id=<staging-account-id>
   ```
   Its state is local. Keep `terraform.tfstate` safe (password manager or a private location) or migrate it into the bucket afterwards with a `backend "s3"` block.
2. **Staging**:
   ```bash
   cd ../envs/staging
   cp backend.hcl.example backend.hcl            # set bucket = <state_bucket output>
   cp terraform.tfvars.example terraform.tfvars  # set aws_account_id
   tofu init -backend-config=backend.hcl
   tofu providers lock -platform=linux_amd64 -platform=darwin_arm64 -platform=darwin_amd64 -platform=windows_amd64
   tofu plan -out=staging.tfplan                 # review, then: tofu apply staging.tfplan
   ```
   Commit the generated `.terraform.lock.hcl` (also do this for `bootstrap/`). From then on CI enforces it.
3. **DNS**: the first apply creates the `zone_name` hosted zone and then waits on certificate validation. Add the `zone_name_servers` output as an NS record for `zone_name` at the parent zone (registrar or the account that owns the domain) while it waits.
4. **Secrets to fill by hand**: `calling-agent-staging/<app>/manual` (Sentry DSNs, Exotel and AI provider keys) start as empty strings. Set them with the console or `aws secretsmanager put-secret-value`; OpenTofu never overwrites them.
5. **Images**: services start from tag `bootstrap` with no image behind it. Push real images through the deploy workflow before the first working-hours scale-up (09:00 IST), or set `scale_to_zero = false` and `desired_count` by hand while bootstrapping.
6. **GitHub**: create Environments `staging` (deployment branch: `main`) and `staging-migrations` (`main` + required reviewer). Set variable `AWS_DEPLOY_ROLE_ARN` = output `github_deploy_role_arn` on both.
7. **App login role**: a one-off ECS task creates the `calling_agent_app` role (member of `api_app`) from the `postgres_app_secret_arn` secret, after the first migration. Built with the compute layer.

## Design notes

- **Secrets**: the schema owner password, app DB login, Redis AUTH token, Core API keys and the ES256 service key pairs are generated by OpenTofu and stored in Secrets Manager, so they are also in state (KMS-encrypted in S3, versioned, access restricted). The owner secret carries a `url` key because the migrate entrypoint reads only `MIGRATION_DATABASE_URL`; only the `api-migrate` task gets it. Rotation is manual for now (replace the `random_password` / `tls_private_key`).
- **Service JWTs (ADR 0011)**: one ES256 key pair per issuer (voice-gateway, voice-worker, scheduler, postcall-worker). Each issuer gets only its own `SERVICE_JWT_PRIVATE_KEY`; the Core API gets all public keys as `SERVICE_JWT_PUBLIC_KEYS` (JSON: issuer to PEM). Names are provisional until Chat 01 implements ES256.
- **Env vars (ADR 0011)**: unprefixed inside each app (`DATABASE_URL`, `REDIS_URL`, `S3_BUCKET`, `PORT`); only another service's URL is prefixed (`CORE_API_URL=http://api.internal:4000`). Every service also gets `OTEL_EXPORTER_OTLP_ENDPOINT` and `OTEL_SERVICE_NAME`.
- **Deploys**: services ignore `task_definition` and `desired_count` changes, so CI-registered revisions and the working-hours schedule are not reverted by `tofu apply`.
- **Recordings** expire at 90 days, the platform retention ceiling (ADR 0012). The module rejects values above 90. Tenants with a shorter `retention_days` are deleted early by the Post-call Worker.
- **Postgres** forces TLS (`rds.force_ssl=1`): connection strings need `sslmode=require`. The owner (RDS master user, `calling_agent`) is not a superuser and has `CREATEROLE`, matching local dev and CI.
- **Redis** is node-based with `maxmemory-policy noeviction` (BullMQ) and TLS + AUTH: URLs are `rediss://`.
- **Data tier** subnets have no route to the internet. Postgres and Redis admit only the workload security group.
- **Deploy role** trusts only jobs bound to the `staging` / `staging-migrations` Environments of this repository; it can push to `calling-agent/*` ECR repos, update services and run one-off tasks in the staging cluster, and pass only `calling-agent-staging-ecs-*` roles to ECS.
